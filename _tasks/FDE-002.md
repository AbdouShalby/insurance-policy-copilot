## Requirements
1. **Arabic retrieval**
   - Add an Arabic text normaliser used for both indexing and queries: strip diacritics (tashkeel) and tatweel, unify alef forms (أ إ آ ٱ → ا), ى → ي, ة → ه, and light prefix stripping for common prefixes (ال، وال، بال، كال، فال، لل) on tokens longer than 3 characters. English behaviour must not change.
   - Implement it in the API's index layer (TypeScript), no new dependency.
   - Add 4-6 more Arabic eval questions; the eval must report Arabic and English hit rates separately.
   - Target: overall hit@3 at least as good as phase 1, and every Arabic question that has an answer in the docs hits at k=3. If one cannot, explain why in the report.
2. **Redis-backed idempotency for the CRM webhook**
   - New store abstraction: `EventStore` with an in-memory implementation (current behaviour) and a Redis implementation using `ioredis` (`SET key value NX EX <ttl>` for claim, store the result JSON, 7-day TTL default via `CRM_EVENT_TTL_SECONDS`).
   - Select Redis when `REDIS_URL` is set, otherwise in-memory. Concurrent duplicates across two API instances must not double-process: the loser of `SET NX` waits briefly for the stored result (poll with a short bounded timeout) and returns it, or returns 409 `processing` if it is not ready in time.
   - Tests: unit tests for both stores; the Redis store tested against a small in-process fake (no real Redis needed in tests). Keep existing webhook tests green.
3. **Demo UI**
   - A single static page served by the API at `/` (plain HTML + small vanilla JS, no framework, no build step): question box, answer, citations list (doc title, page, snippet), mode badge (extractive or llm), RTL rendering when the question or answer is Arabic, and a button to load the sample policies.
   - Accessible, works at phone width, no external CDN.
4. **Docker and local run**
   - `docker-compose.yml` runs ingest, api and redis with healthchecks; the API uses Redis in compose.
   - Add Dockerfiles if missing. Do not require Docker for tests.
   - `scripts/` gets one command per OS to start everything locally without Docker (PowerShell `.ps1` and bash `.sh`), loading the samples.
5. **CI**
   - `.github/workflows/ci.yml`: on push and pull request, run Python tests (3.12), API tests and build (Node 20), and the eval in extractive mode; fail if overall hit@3 drops below 0.85 or not-found accuracy below 1.0.
6. **Dependencies and warnings**
   - Resolve the Starlette/httpx deprecation warning if possible.
   - Run `npm.cmd audit`; fix what can be fixed without major-version breakage; list the rest with severity in the report.
   - Allowed new dependencies: `ioredis` (and its types if needed). Anything else needs a reason under deviations.
7. **Documentation (English, concise, accurate)**
   - `README.md`: what it is (one paragraph), demo screenshot description or ASCII flow, architecture mermaid diagram, quick start (Docker and no-Docker), API reference table, configuration table (all env vars with defaults), testing and eval, project structure, limitations, licence.
   - `docs/case-study.md`: framed as a forward-deployed engineering exercise: the client problem (synthetic broker), constraints, what was built, key decisions and trade-offs (lexical retrieval vs embeddings, extractive fallback, HMAC + idempotency, Redis claim pattern), results (eval numbers from the actual run), what I would do next in a real deployment. No invented metrics.
   - `docs/architecture.md`: components, data flow, sequence diagram (mermaid) for the CRM webhook including retries and duplicate delivery.
   - `docs/deployment-playbook.md`: update for Redis and compose.
   - `docs/verification.md`: update with phase 2 evidence.
   - `CHANGELOG.md` (phase 1 and phase 2) and `LICENSE` (MIT, copyright "Abdelrhman Shalby").
