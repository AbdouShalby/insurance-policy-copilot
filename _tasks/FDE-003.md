# FDE-003: Public read-only demo on Hugging Face Spaces

Lead: Claude. Implementer: Codex. Date: 2026-11-17.

## Objective
Package the project as a single Docker container that runs on a free Hugging Face Docker Space, so anyone can open a public URL and ask questions against the synthetic sample policies, at zero running cost and with no way for visitors to upload content or abuse the service.

## Context
- Read first: `README.md`, `docker-compose.yml`, `apps/api/Dockerfile`, `services/ingest/Dockerfile`, `apps/api/src/app.ts`, `apps/api/src/main.ts`, `apps/api/src/policy.service.ts`, `apps/api/public/` (demo UI), `docs/deployment-playbook.md`.
- Hugging Face Docker Spaces: one container, the app must listen on port 7860 (`app_port` in the Space README front matter), the container runs as a non-root user with uid 1000, and the filesystem outside the user's home/workdir may be read-only. No Redis service is available; the API already supports an in-memory event store when `REDIS_URL` is unset.
- The API needs the Python ingest service to ingest documents. In the demo, both processes run in the same container: ingest on 127.0.0.1:8001 (not exposed), API on 0.0.0.0:7860.
- The index must be seeded with the five sample policies (`POST /samples` logic in `app.ts`) at container start, before the Space reports healthy, so a visitor's first question works with no setup.
- No LLM key will be configured: answers stay in `extractive` mode. Do not add any LLM call path.

## Requirements
1. Demo mode is enabled by an env var `DEMO_MODE=true`. When on:
   - `POST /documents` returns 403 with a clear JSON message ("Uploads are disabled in the public demo").
   - `POST /samples` returns 403 to visitors; seeding happens through an internal startup path (for example a function called from `main.ts` when `SEED_SAMPLES_ON_START=true`, or a seeding step in the start script that calls the API on 127.0.0.1 before the port is published; choose the simplest safe option and explain it).
   - `POST /webhooks/crm` returns 403 (no secret is configured in the demo).
   - `POST /ask` and `GET /health` and `GET /` work normally. Question length stays bounded by the existing DTO; confirm the limit and state it.
   - The UI hides the upload and load-samples controls and shows the read-only note.
   When `DEMO_MODE` is unset, behaviour is exactly as today (all existing tests pass unchanged).
2. Rate limiting on `POST /ask` in demo mode: about 20 requests per minute per client IP, returning 429 with a JSON message. Allowed dependency: `@nestjs/throttler` (official NestJS package, pin an exact current version) OR a small in-memory limiter written in the API if that is simpler; state which and why. Respect `X-Forwarded-For` only as far as needed behind the HF proxy (trust proxy setting), and explain the choice.
3. `deploy/hf/Dockerfile` builds both services from the repo root context, runs as uid 1000, writes the index to a writable path under the app user's home, listens on 7860, and starts ingest then API via a small start script that exits if either process dies. Keep the image reasonably small (multi-stage, slim bases).
4. `deploy/hf/README.md` is the Space README: HF front matter (`title`, `emoji`, `colorFrom`, `colorTo`, `sdk: docker`, `app_port: 7860`, `pinned: false`, `license: mit`, `short_description`), then two or three lines: what it is, synthetic data only, link to the GitHub repo.
5. A script or documented command the lead can run to assemble the Space repo contents (the files HF needs at the Space repo root: `Dockerfile`, `README.md`, and the source it copies). Simplest acceptable form: `deploy/hf/build-space.sh` that copies the required paths into a target folder given as an argument, excluding tests, eval output, node_modules, .env files and `_tasks`.
